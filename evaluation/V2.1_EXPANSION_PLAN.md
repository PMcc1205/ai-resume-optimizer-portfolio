## 3. V2.1 测试集结构与数量

现有 12 条作为不可变 `Core Regression Set`。建议新增 78 条，形成 90 条总套件：

| 集合 | 新增数量 | 主要目的 |
| --- | ---: | --- |
| Normal / Clean Set | 18 | 测量合法改写误杀、False Positive |
| Single-risk Set | 24 | 12 类主要 violation 每类至少两个独立表达 |
| Multi-risk Set | 12 | 双标签、三标签以及多 Rewrite 混合风险 |
| Boundary Set | 12 | 职责、阶段、能力、数字的相邻等级和同义边界 |
| Adversarial Set | 12 | 隐晦表达、被动语态、结果暗示、拆句和自然简历语言 |
| 合计 | 78 | 不含现有 12 条 Core Regression |

建议将 78 条中的 18 条预先划为 Holdout，因此开发可见扩展集为 60 条，Holdout 不是额外增加的数量。

### Normal / Clean Set

至少覆盖：

- 原事实完整保留，仅压缩语句
- 同义词替换但职责等级不变
- 合法调整 STAR 顺序
- 合法合并两个同项目 Fact
- 合法拆分一句为两句
- 保留原数字、指标口径和单位
- 保留 Demo/MVP 等项目状态
- 原 Fact 明确支持结果、技术和方法
- 合法使用部分 Fact，不要求使用全部 Fact

### Single-risk Set

每个案例只引入一个变量。至少为每种 violation 准备两种不同措辞或业务域，避免只验证固定关键词。

### Multi-risk Set

包含职责+数字、技术+结果、跨项目+职责、阶段+独立职责，以及批量 Rewrite 中“多数合法、一条非法”的场景。Gold 使用集合，不依赖标签顺序。

### Boundary Set

成对设计合法/非法最小差异，例如：

- `参与→协助` 与 `参与→负责`
- `MVP→完成 MVP` 与 `MVP→正式上线`
- `负责模块→负责模块交付` 与 `负责模块→主导整体项目`
- `熟悉→了解并使用` 与 `熟悉→精通并独立设计`
- 数字同值同口径与同值异口径

### Adversarial Set

不直接使用“主导、上线、提升”等明显触发词，改用：

- “牵头闭环”“作为唯一 owner”等职责暗示
- “已面向真实用户稳定运行”等上线暗示
- “带来明显改善”“实现规模化应用”等结果暗示
- 跨句、括号、英文缩写和被动语态
- 同一事实在多个项目中拥有相似名称
- 合法事实与虚构事实混排

## 4. Holdout 设计

建议从新增 78 条中预先冻结 18 条：Clean 4、Single-risk 5、Multi-risk 3、Boundary 3、Adversarial 3。

规则：

1. 在任何新规则开发前完成双人 Gold 审核并计算文件哈希。
2. Holdout 不参与 Prompt、规则、阈值或 Gold 调优。
3. 调试阶段只运行 Core Regression + 60 条 development expansion。
4. 每个 release candidate 最多运行一次完整 Holdout；只查看汇总指标，完成决策后再查看失败明细。
5. 一旦某条 Holdout 被用于修复，它立即移入 regression，并补充一条全新未见案例维持 Holdout 数量。
6. Holdout 应跨岗位、项目类型、表达方式和数字口径分层抽样，并去除个人信息。
7. 模型、Prompt、Schema、Runner、Case 或 Gold 任一项变化，都生成新运行版本，不覆盖旧结果。

## 5. 指标计算方案

### Case 级指标

- **Overall Pass Rate** = 完全满足该 Case 所有 Gold 检查的案例数 / 可判定案例数。
- **Exact Violation Set Match** = actual violation 集合与 expected 集合完全一致的案例数 / 可判定案例数。
- Execution Error 不计为普通判断错误，单独报告；同时必须报告 denominator，禁止用排除错误后的 Pass Rate 掩盖运行失败。

### 多标签指标

对每个 violation 分别统计：

- TP：Gold 有该标签且 actual 有。
- FP：Gold 无该标签但 actual 有。
- FN：Gold 有该标签但 actual 无。
- TN：Gold 和 actual 都无。
- Precision = TP / (TP + FP)。
- Recall = TP / (TP + FN)。
- F1 = 2 × Precision × Recall / (Precision + Recall)。
- False Positive Rate = FP / (FP + TN)。
- False Negative Rate = FN / (FN + TP)。

同时输出 micro、macro 和 per-label 指标。无正样本的标签不输出误导性的 0 分，而标记为 `N/A`。

### 产品风险指标

- **Clean Case False Positive Rate** = 被错误判为不通过的合法 Candidate / 全部合法 Candidate。
- **Unsafe Case False Negative Rate** = 被错误判为通过的违规 Candidate / 全部违规 Candidate。
- **Rewrite Permission FP** = 不允许 Rewrite 却被允许调用的案例比例。
- **Rewrite Permission FN** = 合法可改写却被禁止的案例比例。

产品解释：False Positive 会阻断真实、合法的简历优化；False Negative 会放过事实篡改。二者必须分别报告，不能被 Overall Pass Rate 抵消。

### 结构与稳定性指标

- **First-attempt Schema Valid Rate** = 首次模型响应通过 JSON + Schema 的案例数 / 模型调用案例数。
- **Eventual Schema Valid Rate** = 有限重试后获得合法结构的案例数 / 模型调用案例数。
- **Retry Rate** = 发生至少一次重试的案例数 / 模型调用案例数。
- **Execution Error Rate** = 最终执行错误案例数 / 总案例数。

所有指标同时给出分子、分母和 95% Wilson 置信区间；小样本阶段不只展示百分比。

## 6. 推荐执行顺序

1. 审核并签署本 Baseline 清单，禁止覆盖 V2 结果。
2. 先编写 V2.1 Case Schema/命名/Gold 规范，不改 Runner 或产品逻辑。
3. 先创建 18 条 Clean + 12 条 Boundary，优先建立 False Positive 基线。
4. 再创建 24 条 Single-risk，完成每类 violation 的独立覆盖。
5. 创建 12 条 Multi-risk 和 12 条 Adversarial。
6. 在运行前完成 Gold 双审、去重和最小变量检查，并冻结 18 条 Holdout。
7. 只对 60 条 development expansion 做首轮真实 Evaluation；报告错误，不立即改规则。
8. 按错误类型区分模型语义、结构、分类、Gold 歧义和数据问题。
9. 冻结 release candidate 后运行一次 Holdout，输出正式多指标报告。
10. 将确认的真实缺陷转为新的 regression case，创建下一版本 Baseline；旧 Gold 和旧结果永久保留。
